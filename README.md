# Paradata Feature Extraction Pipeline

A research-grade Python project for engineering timing-based features from mobile survey paradata. 

This project analyzes timing data collected from SurveyCTO and ODK surveys and extracts features that can be used to predict survey data quality issues.

## Project Structure

- `data/`: Raw paradata logs and **`ground_truth_labels.csv`** for adversarial validation.
- `docs/`: Formal academic deliverables (Format Guides, Feature Library Manuals, Validation Reports).
- `notebooks/`: **`System_Audit_Report.ipynb`** - The Standardized 15-point interactive audit engine.
- `output/`: Processed feature matrices and visualization plots.
- `report/`: **`final_academic_report.md`** - The 7,000-word thesis structural blueprint.
- `src/`: Core Python library implementing the 4-Layer Validation Engine.
- `tests/`: Automated feature tests and statistical evaluation scripts (`calculate_academic_metrics.py`).

## How It Works

This project is a data engineering pipeline designed specifically to catch "bad actors" or anomalies in mobile survey data collection (like when an enumerator speed-runs a 30-minute survey in 2 minutes, or takes suspicious 15-minute breaks during an interview).

It takes the raw timing logs (paradata/audit files) generated by survey platforms like **SurveyCTO** or **ODK**, where every single button press, question appearance, and swipe is recorded, and mathematically transforms those millions of rows into a clean, single-row summary per interview containing predictive features.

### 1. The Input (Strict CSV Data Format)
You start by placing your raw `.csv` audit logs from SurveyCTO or ODK into the `data/` folder. 
Each `.csv` file MUST strictly adhere to the following column format. **Missing mandatory columns will cause the pipeline to fail or skip features.**

**Mandatory Columns:**
- `interview_id`: A unique identifier for the specific interview or session.
- `start_time`: The timestamp when the event began (e.g., `2023-01-01 10:00:00`).
- `end_time`: The timestamp when the event ended.
- `duration_ms`: The time taken for the event. **All timing values MUST strictly be in milliseconds.**
- `event_type`: The action taken by the user. Expected keywords include: `Question`, `backward`, `back`, `jump_backward`, `forward`, `skip`, `jump_forward`.
- `question_name`: (or `node_name`) The identifier for the specific screen or question that was interacted with.

>  **Note on Units:** Ensure your dataset exports `duration_ms` in milliseconds to avoid massive mathematical discrepancies. If you wish to analyze the final output features in seconds rather than milliseconds, simply divide the resulting columns by 1000 in your Jupyter notebook.

### 2. The 4-Layer Validation Engine
The system utilizes a 4-Layer Architecture to ensure mathematical integrity:
1. **Structural Ingestion:** Enforces CIR (Common Intermediate Representation) parity.
2. **Integrity Layer:** Traps logical bounds (Negative durations, impossible idle times).
3. **Behavioral Layer:** Extracts 40 features (Entropy, Speed Trajectories, Back-Nav).
4. **Classification Layer:** Maps weight-based scores to 3-tier severity bins.

### 3. Execution
Run the automated pipeline on explicit files:
```bash
python run_pipeline.py --inputs data/odk.csv data/surveycto.csv
```

If you also have ground truth labels for a synthetic or otherwise labelled
dataset, pass them in the same command to generate metrics automatically:

```bash
python run_pipeline.py \
  --inputs data/synthetic_datasets/n500/audit_logs_surveycto.csv \
  --ground-truth data/synthetic_datasets/n500/ground_truth_labels.csv \
  --label n500_surveycto
```

### 4. The Output
Each run now writes three first-class artifacts:

- `output/feature_dataset_<label>.csv`: pure per-interview feature matrix
- `output/anomaly_report_<label>.csv`: anomaly scores and review status
- `output/pipeline_output_<label>.csv`: combined feature + anomaly dataset

If `--ground-truth` is provided, the same run also writes:

- `output/predictions_<label>.csv`
- `output/metrics_<label>.csv`
- `output/metrics_<label>.json`
- `output/metrics_<label>.md`

Legacy compatibility files (`output/features_output_*.csv` and
`output/anomaly_report.csv`) are still written, but the labelled artifacts above
are the authoritative outputs for new runs.

Notable features include:

**>  IMPORTANT: All output timing features are recorded in MILLISECONDS.** As a result, variances like `response_time_variance` will appear extremely large compared to seconds. This is normal behavior.

- **Response Time Features:** `mean_response_time`, `median_response_time`, `min_response_time`, `max_response_time`, `response_time_variance`
- **Behavioral/Rhythm Features:** `uniform_speed_score` (std dev of times), `rolling_variance_mean`, `rolling_variance_max`
- **Cognitive/Mechanical Indicators:** 
    - `response_time_entropy`: Captures variability in answering behavior (Shannon Entropy; $H(X) = - \sum p(x) \log p(x)$). Low entropy indicates mechanical, rapid-fire, highly uniform answering (a strong indicator of fake data). High entropy indicates natural human variation.
    - `response_time_skewness` & `response_time_kurtosis`: Describe the shape of the distribution. A negative skew means a long tail on the left (most responses are high duration, with a few very fast ones).
- **Speed Features:** 
    - `total_duration`
    - `speed_index`: Compares interview duration relative to the global dataset median. A `speed_index` of 1.0 means exactly at the median speed.
    - `relative_speed_score`: Relative to global mean.
- **Pause & Navigation Features:** `pause_count`, `total_pause_duration`, `average_pause_length`, `backtrack_count`, `forward_jump_count`, `straightlining_count`.
    - `screen_revisit_rate`: Normalized between `0.0` (no revisits) and `1.0` (revisited every single question).
- **Anomaly Detection:** `is_anomalous` (0 or 1). Because survey timing data is heavily skewed (non-normal), we use **Robust IQR (Interquartile Range)** bounds rather than naive Z-scores. An interview is flagged if its total duration falls outside $Q1 - 1.5*IQR$ or $Q3 + 1.5*IQR$.

## Recalibration for New Datasets

The pipeline was optimized on synthetic validation data. For best performance on new real-world datasets, recalibrate the anomaly detection parameters:

### Threshold Recalibration
Find the optimal anomaly threshold for your data distribution:

```bash
python threshold_recalibration.py --data-paths data/your_data.csv --ground-truth data/your_labels.csv
```

This will:
- Run ROC analysis on your data
- Find the optimal threshold (currently set to 2.0)
- Generate ROC curve plots
- Save results to `output/threshold_recalibration_results.txt`

### Feature Validation
Identify which features are statistically significant for your dataset:

```bash
python feature_validation.py --data-paths data/your_data.csv --ground-truth data/your_labels.csv
```

This will:
- Perform Mann-Whitney U statistical tests
- Apply Bonferroni correction for multiple testing
- Identify significant features (currently 20 features validated)
- Save detailed results to `output/feature_validation_results.txt`

### Updating the Pipeline
After recalibration:
1. Update `src/validation/anomaly_detector.py` with the new threshold
2. Adjust feature weights based on significance testing results
3. Re-run validation to confirm thesis requirements are met

### Generalizability Notes
- **Parser fixes and event mappings**: Work for any SurveyCTO/ODK data
- **Pipeline architecture**: Modular design handles any survey data
- **Threshold and features**: May need recalibration for different survey types/contexts
- **Statistical methods**: ROC analysis and feature testing are universally applicable
