# Paradata Feature Extraction Pipeline

A research-grade Python project for engineering timing-based features from mobile survey paradata. 

This project analyzes timing data collected from SurveyCTO and ODK surveys and extracts features that can be used to predict survey data quality issues.

## Project Structure

- `data/`: Raw paradata logs and **`ground_truth_labels.csv`** for adversarial validation.
- `docs/`: Formal academic deliverables (Format Guides, Feature Library Manuals, Validation Reports).
- `notebooks/`: **`System_Audit_Report.ipynb`** - The primary interactive audit notebook.
- `output/`: Processed feature tables, anomaly reports, metrics, and plots.
- `report/`: **`final_academic_report.md`** - The full project report (Word and PDF versions in `docs/deliverables/`).
- `scripts/`: Reproducible workflow, validation, calibration, plotting, and audit commands.
- `src/`: Core Python library for parsing, feature extraction, anomaly detection, and reporting.
- `tests/`: Automated parser, feature, pipeline, validation, and end-to-end tests.

## How It Works

This project is a data engineering pipeline for identifying unusual timing and navigation patterns in mobile survey data collection.

It takes the raw timing logs (paradata/audit files) generated by survey platforms like **SurveyCTO** or **ODK**, where every single button press, question appearance, and swipe is recorded, and transforms them into:
- question-level feature tables
- section-level feature tables
- a single-row-per-interview feature dataset
- an anomaly report for review and QA

### 1. The Input (Supported Raw Audit Formats)
You start by placing raw `.csv` audit logs from SurveyCTO or ODK into the `data/`
folder, or by passing explicit files with `--inputs`.

The current pipeline supports the raw benchmark formats documented in
`docs/paradata_format_guide.md`:

- SurveyCTO-style logs:
  - required benchmark columns: `interview_id`, `node`, `event`, `start`, `end`, `duration_ms`
  - `start` and `end` are numeric epoch milliseconds
- ODK-style logs:
  - required benchmark columns: `instance_id`, `name`, `event`, `start_time`, `end_time`
  - `start_time` and `end_time` are ISO 8601 timestamps

The parsers also support alternative platform-specific names such as:
- `interview_id` or `instance_id`
- `question_id` or `name`
- `start_time` / `end_time`
- `duration_ms`

> **Note on Units:** All normalized pipeline timing features are emitted in
> milliseconds. When the raw input already contains numeric timestamps, the
> parser assumes epoch milliseconds unless the values look like epoch seconds,
> in which case it scales them to milliseconds automatically.

### 2. Processing Stages
The pipeline uses transparent, reproducible stages:
1. **Parse:** Convert SurveyCTO or ODK audit logs into the Common Intermediate Representation (CIR).
2. **Extract:** Compute question-level, section-level, survey-level, and statistical timing features.
3. **Detect:** Apply IQR-based statistical flags and rule-based behavioral checks.
4. **Report:** Export feature tables, anomaly reports, and labelled validation metrics when ground truth is supplied.

### 3. Execution
The repository ships with a small ready-to-run sample: `data/surveycto.csv`,
`data/odk.csv` and matching labels in `data/ground_truth_labels.csv`. The
sample is a documented product of the synthetic generator
(`python tests/generate_synthetic_final.py --overwrite`, seed 42, 24 labelled
interviews across both formats). Run the pipeline on it directly after
cloning:
```bash
python run_pipeline.py --inputs data/odk.csv data/surveycto.csv
```

If you also have ground truth labels for a synthetic or otherwise labelled
dataset, pass them in the same command to generate metrics automatically:

```bash
python run_pipeline.py \
  --inputs data/synthetic_datasets/n500/audit_logs_surveycto.csv \
  --ground-truth data/synthetic_datasets/n500/ground_truth_labels.csv \
  --label n500_surveycto
```

### 4. The Output
Each run now writes five first-class artifacts:

- `output/question_features_<label>.csv`: one row per `interview_id + field_name`
- `output/section_features_<label>.csv`: one row per `interview_id + section_name`
- `output/feature_dataset_<label>.csv`: pure per-interview feature matrix
- `output/anomaly_report_<label>.csv`: anomaly scores and review status
- `output/pipeline_output_<label>.csv`: combined feature + anomaly dataset

If `--ground-truth` is provided, the same run also writes:

- `output/predictions_<label>.csv`
- `output/metrics_<label>.csv`
- `output/metrics_<label>.json`
- `output/metrics_<label>.md`

If you need the older compatibility filenames, run the pipeline with
`--write-legacy-outputs`. Otherwise the labelled artifacts above are the
authoritative outputs for new runs.

All output timing features are recorded in milliseconds. Large variance values are expected because the calculations are performed on millisecond-scale response times.

The implemented feature families are:

- **Question-level (`Q-01` to `Q-10`):** response time, first interaction time, edit count, revisit indicators, idle time, keystroke/event count, constraint count, and first-to-last interaction duration.
- **Section-level (`S-01` to `S-10`):** section pace, duration, within-section variance, pace ratio, pause counts, pause durations, back-navigation count, and completion rate.
- **Survey-level (`V-01` to `V-10`):** total interview duration, early/late speed trajectory, back-navigation rate and count, time-of-day, day-of-week, session-length ratio, and zero-back-navigation flag.
- **Statistical (`T-01` to `T-10`):** response-time variance, IQR, entropy, skewness, kurtosis, mean, median, coefficient of variation, minimum, and maximum.
- **Anomaly report:** `anomaly_score`, `status`, `iqr_flags`, `rule_flags`, `flagged_features`, and binary prediction columns for labelled validation.

The anomaly score is reproducible from the exported flags. IQR outlier dimensions are grouped into a single score contribution to avoid double-counting correlated duration, mean, and variance outliers from the same underlying timing pattern.

### 6. Analysis & Jupyter Notebooks
Once you have a pipeline output such as `output/pipeline_output_<label>.csv`, you use the **Jupyter Notebooks** in the `notebooks/` folder.
The notebook is where the actual research and data science happen. Instead of terminal commands, it gives you an interactive, visual environment where you can:
- Import a selected pipeline output or feature dataset.
- Inspect the matching question-level and section-level tables for the same run.
- Run statistical tests (from `src.validation`) to see if the fast response times correlate with poor data quality.
- Generate charts and graphs (from `src.visualization`) to visually prove your findings for academic publication.

## Recalibration for New Datasets

The pipeline was optimized on synthetic validation data. For best performance on new real-world datasets, recalibrate the anomaly detection parameters:

### Threshold Recalibration
Find the optimal anomaly threshold for your data distribution:

```bash
python scripts/threshold_recalibration.py --data-paths data/your_data.csv --ground-truth data/your_labels.csv
```

This will:
- Run ROC analysis on your data
- Find the optimal threshold for the supplied dataset (the latest full n500 recalibration selected `1.10`)
- Generate ROC curve plots
- Save results to `output/threshold_recalibration_results.txt`
- Write a reusable detector config to `output/detector_config_recalibrated.json`

Apply the recalibrated detector settings on a later run with:

```bash
python run_pipeline.py --detector-config output/detector_config_recalibrated.json --inputs data/your_data.csv
```

### Feature Validation
Identify which features are statistically significant for your dataset:

```bash
python scripts/feature_validation.py --data-paths data/your_data.csv --ground-truth data/your_labels.csv
```

This will:
- Perform Mann-Whitney U statistical tests
- Apply Bonferroni correction for multiple testing
- Report Cohen's d as the primary effect size, alongside a supplementary rank-biserial statistic from Mann-Whitney U
- Evaluate the engineered interview-level feature set for the supplied labelled dataset
- Save detailed results to `output/feature_validation_results.csv`

### Updating the Pipeline
After recalibration:
1. Save the generated detector config from `threshold_recalibration.py`
2. Apply it on later runs with `--detector-config`
3. Re-run validation to confirm thesis requirements are met

### Generalizability Notes
- **Parser fixes and event mappings**: Work for any SurveyCTO/ODK data
- **Pipeline architecture**: Modular design handles any survey data
- **Threshold and features**: May need recalibration for different survey types/contexts
- **Statistical methods**: ROC analysis and feature testing are universally applicable

## Synthetic Data And Ground Truth

The canonical synthetic generator now writes the audit logs and a matching
ground-truth label file together:

```bash
python tests/generate_synthetic_final.py --overwrite
```

This produces:
- `data/surveycto.csv`
- `data/odk.csv`
- `data/ground_truth_labels.csv`

For a non-destructive validation bundle under a dedicated directory:

```bash
python tests/generate_synthetic_final.py --output-dir data/workflow_validation/canonical_validation
```

Timestamped runs under `data/synthetic/<timestamp>/` also include their own
`ground_truth_labels.csv`.

For fresh larger benchmark packs, generate both SurveyCTO and ODK exports plus
ground truth with:

```bash
python tests/generate_benchmark_datasets.py --dataset-size 500 --seed 42 --output-dir data/generated_benchmarks/n500_seed42
```

The default synthetic profiles are intentionally clean so they can serve as a
repeatable contract test. To test a less separable, more realistic benchmark,
use the stress profile:

```bash
python tests/generate_benchmark_datasets.py --dataset-size 500 --seed 42 --difficulty stress --output-dir data/generated_benchmarks/stress_n500_seed42
```

To validate repeated fresh synthetic runs and check the acceptance contract
directly, use:

```bash
python scripts/validate_production_readiness.py --sizes 120 500 --seeds 11 42 --formats surveycto odk
```

For stress validation, write results to a separate folder and interpret the
metrics as a robustness check rather than a guaranteed acceptance gate:

```bash
python scripts/validate_production_readiness.py --sizes 500 --seeds 11 42 --formats surveycto odk --difficulty stress --data-root data/stress_benchmarks --output-dir output/stress_validation
```
